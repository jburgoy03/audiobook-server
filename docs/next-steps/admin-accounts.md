# Next steps: the admin page (users and libraries)

Goal: everything the admin does routinely happens on one page in the web client,
not in the browser console.

- **Users:** Dean opens **Admin**, types a name, and gets a temporary passphrase to
  hand over. The new user signs in with it, is made to choose their own passphrase,
  and then sees the public library (LibriVox) and nothing else.
- **Libraries:** add a library, make it public or private, set its credit, and scan
  or force-rescan it, with buttons instead of console snippets.

Why the Libraries section is here and not later: until it exists, every scan or
visibility change means pasting `fetch` calls into the console of an admin session
(with Chrome's paste guard switched off by `allow pasting`). Nothing reviews them,
they aren't repeatable, and the runbook ended up holding JavaScript. Server-side
jobs that don't belong in a browser at all (passphrase recovery, scans without the
100-second limit) go to the command-line tool:
[`admin-cli.md`](admin-cli.md).

[`users-and-public-library.md`](users-and-public-library.md) section 3. Invites
(option B) come after and reuse most of this: the admin page, the passphrase page,

## 1. Server

### Data

`User.MustChangePassword` (bool, default false), migration
`AddMustChangePassword`. Existing users (Dean) get false.

Why a column and not "is the password temporary" from somewhere else: it survives
restarts, it's per user, and resetting someone's passphrase later sets it again.

### Claims and enforcement

- `AudiobookClaimsPrincipalFactory` adds `must_change_password: true` when the flag
  is set, alongside `admin`.
- **Enforced on the server, not just routed in the client.** The fallback policy
  gains a requirement: no `must_change_password` claim. The few endpoints a user
  needs in that state opt into a looser `SignedIn` policy: `GET /api/auth/me`,
  `POST /api/auth/change-password`, `POST /api/auth/logout`. Everything else answers
  403 until the passphrase is changed.
  Why bother, when Dean is the one who knows the temporary passphrase? Because a
  temporary passphrase travels (a text message, a note), and "must change" that the
  server doesn't enforce is only a suggestion.
- `/api/auth/me` returns `mustChangePassword`.

### Endpoints

All under `/api/admin/users`, in a group with `RequireAuthorization(AuthPolicies.Admin)`.

| | |
|---|---|
| `GET /api/admin/users` | `[{ id, username, isAdmin, createdAt, disabled, mustChangePassword, lastSeenAt }]`. `lastSeenAt` is the latest `Device.LastSeenAt`; null if they've never played anything. |
| `POST /api/admin/users` | `{ username }` → 201 `{ id, username, temporaryPassword }`. The passphrase is generated by the server and returned **once**; only its hash is stored. 409 if the name is taken (an admin may learn that). 400 for Identity's validation errors, passed through. |
| `POST /api/admin/users/{id}/reset-password` | New temporary passphrase, returned once; sets `MustChangePassword`; ends their sessions. |
| `POST /api/admin/users/{id}/disable` | `LockoutEnd = DateTimeOffset.MaxValue`, security stamp updated. 400 for your own account. |
| `POST /api/admin/users/{id}/enable` | `LockoutEnd = null`, failed-attempt count reset. |

And for every signed-in user:

| | |
|---|---|
| `POST /api/auth/change-password` | `{ currentPassword, newPassword }`. `ChangePasswordAsync` (which updates the stamp, so other sessions end), clears `MustChangePassword`, then re-issues the caller's cookie (`RefreshSignInAsync`) so this session survives with fresh claims. Bearer clients sign in again. |

Details to get right:

- **Temporary passphrase:** 20 characters from `RandomNumberGenerator`, in an
  unambiguous alphabet (no `0/O`, `1/l/I`), grouped in fours with hyphens so it can
  be read aloud. Meets the 12-character rule with room to spare.
- **Reset without token providers.** `AddIdentityCore` registers none, so reset is
  `RemovePasswordAsync` then `AddPasswordAsync`, not the reset-token flow. Both run
  the stamp update.
- **No promote or demote endpoint yet.** `SetAdminAsync` exists for when it's wanted.
  One admin is the plan.
- **Disabled vs locked out at login.** Both make `PasswordSignInAsync` report
  `IsLockedOut`, and today that's always "Too many failed attempts", which would
  confuse a disabled user. When locked out *and* the account is disabled *and*
  `CheckPasswordAsync` says the passphrase is right, answer 403 "This account is
  disabled." Only someone holding the right passphrase learns that, so it reveals
  nothing to a guesser.
- **How fast a disable bites.** Refresh tokens: immediately (stamp check). Cookies:
  at the next stamp validation, 30 minutes by default. **Lower it to 5 minutes**
  (`SecurityStampValidatorOptions.ValidationInterval`), one small query per user per
  5 minutes. Access tokens: until they expire (1 hour); accepted.

### Tests (integration)

- Every `/api/admin/users*` route: 403 for a non-admin (cookie and bearer), 401
  anonymous. Add them to `AdminTests.AdminRoutes` and `AuthTests.ProtectedRoutes`.
- Create → sign in with the temporary passphrase → `/me` says `mustChangePassword`
  → `GET /api/books` is 403 → change it → `GET /api/books` is 200 and shows only the
  public library → the temporary passphrase no longer works.
- The cookie that changed the passphrase keeps working (`RefreshSignInAsync`); a
  second session of the same user doesn't (refresh token rejected).
- Duplicate name 409. Short passphrase on change 400.
- Disable → their refresh token is rejected → login with the right passphrase is 403
  "disabled", with a wrong one the usual answer → enable → login works.
- The admin can't disable themselves.
- Reset → old passphrase fails, new one works, `mustChangePassword` is set again.
- The visibility matrix already covers what the new user can see; it doesn't change.

## 2. Web client

### Admin page (`/admin`)

- **Masthead:** an "Admin" link next to "Sign out", only when `auth.isAdmin`.
  Convenience only: the server is what enforces it.
- **Route:** `/admin`, rendered only for admins. A non-admin who types the URL gets
  the library (the API would 403 anyway).
- **Users section:** a list (name, admin badge, created, last listened, disabled,
  "must change" state) and an **Add listener** form with just a name field.
- **After creating:** a panel showing the temporary passphrase with a Copy button and
  one line: "They'll choose their own when they first sign in. This won't be shown
  again." The passphrase lives in component state only, never in storage, and is
  gone on navigation.
- **Per-user actions:** Reset passphrase (same one-time panel), Disable or Enable.
  Disable asks for confirmation inline (no `window.confirm`).
### Libraries section

The library endpoints already exist and are admin-only. This is UI on top of them.

- **List:** name, root path, public or private, credit, book count, last scan
  (started and completed).
- **Public toggle** per library (`PATCH { isPublic }`). Making a library public asks
  for confirmation inline, saying how many books it exposes; making it private
  doesn't need to.
- **Credit:** editable inline (`PATCH { credit }`); empty removes it.
- **Scan** and **Force rescan** buttons (`POST …/scan`, `?force=true`). Disabled
  while a scan is running, with the result shown afterwards (`booksAdded`,
  `booksUpdated`, `booksRemoved`, `failures`, `filesDurationCorrected`). Force rescan
  says what it's for ("after scanner changes; re-reads every file").
- **The 100-second limit, honestly handled.** A scan runs inside the request, and
  through Cloudflare it's cancelled after 100 seconds. Until background scanning
  exists, the Scan buttons show a warning when the page isn't on the Tailscale
  address (`location.hostname !== '100.83.139.4'`, or better, a flag from the
  server): "Large scans can time out through the public site. Use the Tailscale
  address or `admin scan` on the server." Small scans (a new LibriVox book) are fine
  either way.
- **Add library:** name, root path, public, credit. The server already checks that
  the path exists; show its message.

Design: the existing system. EB Garamond, bone on black, red only for position. A
form, a table and a one-time panel need no new tokens. Check at 375 as well, since
handing over a passphrase is likely to happen on a phone.

### Choose-your-passphrase page

- `auth.ts` keeps `mustChangePassword` from `/me`. While it's true, `App` renders
  only the passphrase page (no library, no `PlayerProvider`), much as it renders
  the sign-in page while signed out. That matches the server, which would 403 the
  library anyway.
- Fields: current (temporary) passphrase, new, confirm. 12+ characters, said plainly.
  Show the server's message on failure.
- On success: re-fetch `/me`, and the app opens on the library.
- Also reachable voluntarily later ("Change passphrase" in the masthead), using the
  same page without the forced state. Optional in this step.

### Client plumbing

- `api/client.ts`: `adminUsers()`, `createUser(username)`, `resetPassword(id)`,
  `disableUser(id)`, `enableUser(id)`, `changePassword(current, next)`,
  `libraries()`, `createLibrary(…)`, `updateLibrary(id, …)`, `scanLibrary(id, force)`.
- `api/types.ts`: `AdminUser`, `CreatedUser`, `ScanReport`, `mustChangePassword` on
  `CurrentUser` (`Library` already has `isPublic` and `credit`).
- Today only 401 is special in the client. A 403 from an admin call should show "You
  don't have access to this" rather than sign the user out.
